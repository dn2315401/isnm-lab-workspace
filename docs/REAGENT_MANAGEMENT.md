# 원료 라이브러리·시약 관리 개편 — 2026-11-24 v1

현재 작업 브랜치: `work/2026-11-24-v1` (같은 날짜 작업본에 누적 저장). 기존 main과 날짜 브랜치는 유지합니다.

## 사용 방법

1. 원료물질 DB에서 물질을 검색합니다. 기본 목록은 현재 사용 중인 시약만 표시합니다. 시약이 없어도 물질 정보 행을 통해 상세·재구매에 접근할 수 있습니다.
2. 이미 등록된 물질의 새 병은 **새 시약 등록** 또는 **이전 정보로 재등록**을 사용합니다. 새로운 화학물질 등록과 구분합니다.
3. 이전 제조사·제품번호·구매처·보관 위치·단위를 가져옵니다. 구매일·입고일·유효기간·개봉일·용량·잔량·제조 Lot·내부 식별번호는 새로 입력합니다. 이전 값은 참고로 표시하며 자동 확정하지 않습니다.
4. 실제 입고일·양수 용량·보관 위치를 확인하여 저장하면 기존 material_id 아래 새 reagent_id가 생성됩니다. 제조 Lot가 같아도 서로 다른 병을 등록할 수 있습니다.
5. 사용 완료·폐기·유효기간 만료 상태를 날짜·사유와 함께 저장합니다. 이전 상태와 복원 이력을 남깁니다. 완료·폐기 병은 기본 목록에서 숨고 전체 이력에서 볼 수 있습니다.
6. 상세 화면의 구매·사용 이력에서 병별 실험 목록을 봅니다. 공용 사용 이력에서는 시약 ID로 필터하고 원본 스냅샷·계획량·실제량을 확인합니다.

## DB 구조

- `material_entities`: 기존 물질 기본 정보. 재구매로 새로운 Material을 만들지 않습니다.
- `material_reagents`: 개별 구매 시약. material_id FK, 독립 reagent_id, 내부 식별번호, 제조사·제품번호·구매처·날짜·용량·잔량·보관 위치·유효기간·선택 제조 Lot·메모 및 상태를 보관합니다. 상태는 Active/Completed/Expired/Disposed이며 기존 Archived는 과거 자료 보존용입니다.
- `material_reagent_history`: 변경 전/후 상태, 적용 날짜, 사유, 작업자, 당시 시약 정보 스냅샷을 누적합니다. 새 입고 및 정보 확인도 기록합니다.
- `material_orders`: 실제 입고 전 발주 요청·발주 완료·배송 중·취소·입고 완료. 한 주문에 여러 개별 시약이 연결됩니다.
- `material_usages.reagent_id`: 기존 실험 사용 행에 추가한 FK. 물질이 다른 시약은 API와 DB 트리거에서 차단합니다. 사용 완료·폐기해도 이 FK와 원본 스냅샷을 삭제하지 않습니다.
- `material_pre_reagent_backup`: 마이그레이션 직전 물질·기존 Lot·사용 행의 원본을 보존합니다.

기존 `material_lots`와 lot_id는 내부 호환 참조로 유지합니다. 새 시약은 reagent_id와 같은 불투명 호환 anchor를 사용하며, 제조 Lot 번호가 시약의 고유 ID가 되지 않습니다. 제조 Lot별 중복 제한을 새 병 등록에 적용하지 않습니다. 자체 합성은 기존 source_experiment_id를 가진 생산 배치를 유지하고 구매 시약 테이블로 변환하지 않습니다.

## 선택·합성 연결

공통 선택기는 Material을 검색한 뒤 현재 사용 가능한 시약이 1개면 자동 선택하고, 여러 개면 직접 선택하게 합니다. 시약이 없으면 등록 안내를 표시합니다. 계획 단계는 물질만 선택할 수 있으며 실제 기록에는 미등록 상태를 명확히 남길 수 있습니다. DBU·DPA 촉매 바로가기는 공용 Material ID와 선택한 시약 ID를 연결합니다. 촉매·용매·세척액 요약은 기존 동일 사용 행을 공유하여 중복 행을 만들지 않습니다.

새 사용 기록에는 material_id·reagent_id와 과거 호환 lot_id가 함께 저장됩니다. 재구매·현재 병 변경은 이미 저장된 실험의 시약 ID를 새 병으로 바꾸지 않습니다. 실제 사용량과 계획량은 별도이며 재고를 자동 차감하지 않습니다. 사용 불가능 상태의 시약으로 새 실제 사용 기록을 만드는 서버 요청은 거절하지만 기존 기록은 보존합니다.

## 발주·입고

기존 코드 조사에서 독립적인 실제 발주 저장소·API는 없었습니다. 원료 라이브러리의 **재고·발주 알림** 한 곳에서 발주를 등록·갱신하고 배송 중 상태와 시약 없는 소진 물질을 표시합니다. 별도 발주 페이지를 중복 생성하지 않았습니다.

배송 중에는 시약이 생성되지 않습니다. 실제 입고일·병당 용량·병 수·보관 위치를 확인하여 주문 전체를 입고 처리합니다. 각 병에 다른 reagent_id를 부여하고 order_id를 연결합니다. 재시도·동시 처리에 의한 중복 생성을 막습니다. 현재는 주문 전체를 한 번에 입고하는 방식이며, 부분 입고·분할 배송은 지원하지 않습니다 (1회 최대 20병).

## 마이그레이션·백업·복구

`drizzle/0002_reagent_lifecycle.sql`은 추가 전용입니다. 기존 테이블·기존 ID·스냅샷을 삭제하거나 바꾸지 않습니다. 먼저 백업 테이블을 채운 후 새 테이블과 FK를 추가합니다.

기존 Lot에 구매 재고가 있거나 원료 payload의 unassignedInventories에 개별 재고가 있으면 원본을 포함하는 시약 검토 행을 만듭니다. 양수 용량·지정 보관 위치·유효한 구매/개봉/입고 날짜가 함께 있는 자료만 개별 시약 후보로 확인합니다. 그 외는 review_required=1로 기본 활성 선택에서 제외합니다. 기존 정보 확인 화면에서 실제 입고 정보를 확인하면 활성 시약으로 사용할 수 있습니다. 생산 배치 자체나 의미가 불분명한 제조 배치 ID는 구매 시약으로 단정하지 않습니다.

- 배포 전 운영 DB 확인: 원료 86종, 실제 기존 Lot 행 0건, 공용 사용 행 0건, 원료 내 별도 재고 기록 1건. 브라우저에만 있는 실험은 이 숫자에 포함되지 않습니다.
- 운영 적용 결과는 이 문서 하단에 기록합니다. 브라우저에 남은 자료는 기존 백업 키와 공용 import 검토 절차를 통해 로그인 시 대조됩니다. 불확실한 자료의 임의 연결은 하지 않습니다.
- 복구 시 먼저 새 버전의 쓰기를 중지하고 Sites의 이전 저장 버전을 재배포할 수 있습니다. DB는 추가 구조를 유지합니다. 새 시약·발주·새 실험을 삭제하는 다운 마이그레이션은 제공하지 않습니다. 원본 확인·복원은 백업 테이블과 기존 payload를 대조하여 필요한 행만 복원합니다. 신규 데이터가 있는 전체 테이블 덮어쓰기는 금지합니다.
- SQLite 통합 테스트에서 변경 전 payload와 실험 스냅샷의 동일성을 확인했습니다.

## 검색과 UI

일반 화면의 Lot 중심 명칭을 사용 원료·사용 시약 선택·새 시약 등록·사용 시약 미등록·시약 사용 이력으로 변경했습니다. 제조 Lot는 시약 상세의 선택 정보로만 남깁니다. 기존 흰색·남색/검정 텍스트·블루 포인트, 테이블·상태 색상·날짜 입력 방식을 유지합니다.

검색은 시약 ID·내부 번호·제조사·제품번호·구매처를 포함하며 실제 합성의 계획 시약과 실제 시약을 별도로 추적합니다. 기존 Lot 검색 조건과 과거 링크는 호환합니다. 사용 완료·폐기는 기본 검색에서 숨고 과거 이력 포함 시 조회됩니다. 다른 기기의 실험은 원료 상세의 공용 사용 이력에서 볼 수 있습니다. 전체 연구 데이터 검색의 실험 원본은 여전히 현재 브라우저 기준입니다.
